# Product, UX, Engineering and AI Decisions

## What customer problem are we solving?

Guests on a hotel website have simple questions (check-in time, pool, breakfast, cancellation, which room fits three people) and want to know if rooms are available. Today they hunt through pages or call or email the front desk, and many leave without booking. The assistant gives instant, accurate answers and gets them to an availability result in a few taps, and it hands off to a human when it cannot answer reliably.

## Guest journey

1. Land on the page. A welcome message and suggested questions show what the assistant can do.
2. Ask a question, either by typing or by tapping a suggestion, and get a short grounded answer.
3. Ask follow-ups ("and check-out?"), because the conversation remembers context.
4. Tap **Check availability**, or ask about rooms. If dates or guests are missing, the form opens automatically with the missing fields highlighted.
5. See room cards with capacity, features, price per night, total and scarcity ("Only 1 left"), and continue with "Ask about this room".
6. If something fails, see a clear message with a retry button, and the front-desk contact when the answer isn't available.

## Why this frontend design

- **Chat as the primary surface** because the questions are open-ended, and follow-ups feel natural.
- **A form for availability instead of asking three questions in chat.** Dates and guest count are structured data, and date pickers prevent format errors. It opens automatically when the model detects missing information, so the guest never has to find it.
- **Suggested questions** remove the blank-page problem and teach the guest what is answerable.
- **Cards for results** because prices and room options are scanned and compared, not read as a paragraph.
- **Every failure has a visible state:** typing indicator while waiting, error card with retry, offline banner, highlighted fallback bubble.
- Mobile first: a full-height layout, touch-sized controls, safe-area padding, and a form that scrolls within the viewport.
- Accessibility: labelled controls, `role="log"` on the conversation, `role="alert"` on errors, visible focus and reduced-motion support.

## What uses AI and what stays deterministic

| Uses the LLM | Deterministic (no LLM) |
|---|---|
| Understanding free-text questions and follow-ups | Availability, room capacity filtering and pricing |
| Composing a short natural answer from the hotel data | Date and guest validation, including re-validating dates the model produces |
| Deciding whether a message is an availability request, and extracting dates and guests | Availability-form submissions (they skip the LLM entirely) |
| Resolving relative dates ("next Friday") using today's date | Result messages and room cards |
| | Fallback text, error messages, session handling |

The rule: the model interprets language, and code decides facts and money.

## What can go wrong with the AI response

- **Hallucination:** inventing a policy, price or amenity that isn't in the data.
- **Wrong tool arguments:** for example misreading "next weekend", or inventing a guest count.
- **Accepting a false premise:** for example "since breakfast is included…".
- **Prompt injection:** a guest tells the model to ignore its rules or reveal the prompt.
- **Overlong or off-topic answers.**
- **Latency, timeouts or provider outages.**

## Preventing hallucinations and unsupported answers

1. The system prompt tells the model to answer only from the supplied hotel data, and gives it a `cannot_answer` tool, so "I don't know" is a first-class outcome rather than a guess.
2. Availability and prices never come from the model. It can only call the tool, and the numbers come from code.
3. Tool arguments are validated in code. Past or inconsistent dates go back to the guest as a request to re-enter them.
4. The prompt has an explicit rule to correct wrong assumptions using the data.
5. Low temperature (0.2) and short answers.
6. Guest text is only ever sent as a user message, never inserted into the system prompt, and the prompt tells the model to treat it as untrusted.
7. Unknown tools and empty output become a safe fallback.

Honest limitation: free-text answers are still generated by the model, and we don't yet verify each one against the data. The production plan below covers that.

## When the model, frontend call or a dependency fails

- **Model timeout or provider error:** the backend returns HTTP 200 with `type: error` and a friendly message that includes the front-desk contact. The frontend shows it in the chat with **Try again**. The failed turn isn't saved to history.
- **Missing API key:** the app still starts and reports the same friendly error. Availability through the form keeps working.
- **Network failure or timeout in the browser:** the client maps it to a typed error and shows a retry card. Validation errors (422) show the reason and don't offer a pointless retry.
- **Unexpected backend bug:** a structured HTTP 500 with a request id, no internals leaked.
- **Offline:** an offline banner appears.

## How to measure whether it is useful

- **Resolution rate:** conversations where the guest got an answer and did not go to the front desk. This is the core metric.
- **Availability funnel:** availability intent → form completed → results viewed → click-through to booking.
- **Fallback rate and top fallback questions,** which show gaps in the knowledge base.
- **Answer accuracy:** a weekly human review of a sample of conversations, plus an automated eval set (the scenarios in `EVALUATION.md`) run against the live model on every prompt or model change.
- **Guest feedback:** thumbs up/down on answers.
- **Operational:** p50 and p95 latency, error and timeout rate, cost per conversation.
- **Business:** front-desk call and email volume for FAQ topics, and bookings that started in chat.

## What I would improve before production

1. Connect `check_availability` to the real booking system or property management system, with caching, and hand off to the booking flow with the dates pre-filled.
2. Move sessions to Redis, and add rate limiting, bot protection and CORS/host hardening.
3. Verify answers after generation: check prices and times mentioned in a response against the knowledge base, and fall back if they don't match.
4. Run the evaluation set in CI against the live model, and add a regression alert on the fallback rate.
5. Stream responses to improve perceived speed.
6. Add feedback buttons, analytics and tracing, and log with PII redaction.
7. Human handoff (WhatsApp, phone or email) with the conversation transcript.
8. Retrieval over a larger knowledge base with content managed by hotel staff, not a JSON file.
9. Multilingual support, especially Hindi and regional languages, plus an accessibility audit.
10. Deployment pipeline: containers, CI for backend and frontend tests, secrets management, monitoring.

## Engineering decisions (short)

- **FastAPI and Pydantic:** typed contracts, automatic validation and free API docs.
- **LLM behind an interface:** switching from Claude to Gemini touched one file, and tests use a scripted `FakeLLM`, so they are deterministic and free.
- **Tool calls decide the response type,** instead of parsing free text, so the frontend receives a clean `type` field.
- **Structured errors everywhere:** a request id ties frontend, API response and logs together.
- **Full knowledge base in the prompt,** because the data is small. Retrieval would add complexity and a new failure mode.
- **In-memory sessions:** fine for a demo, and it's noted as a production gap.
